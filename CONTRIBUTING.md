# Contributing

This is the engineering playbook for the AuditGen repo. Keep it short, keep it true, update it when reality changes.

## Branches

```
main      = stable baseline. Do not push directly. Merges via PR only.
develop   = active integration. Default base for feature branches.
feature/* = short-lived; branch from develop, PR back into develop.
security/*= same shape, security-sensitive changes.
docs/*    = docs-only.
hotfix/*  = emergency only; branch from main, fast-track review.
autopilot/* = generated by the night-autopilot agent.
```

Open PRs **into `develop`**. Merge to `main` happens via release cuts.

## Local setup

```bash
cp .env.example .env       # fill in real values for the providers you actually use
npm install                 # postinstall runs prisma generate
npm run db:push             # sync schema to a local Postgres (or pointed instance)
npm run dev                 # http://localhost:3000
```

You'll need a Postgres instance reachable via `DATABASE_URL`. Easiest local option:

```bash
docker run -d --name audgen-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16
```

If you only need to lint/test, you can use a placeholder URL — `zod` only parses the env, it doesn't connect.

## Daily commands

```bash
npm run lint        # eslint with --max-warnings 0
npm run typecheck   # tsc --noEmit
npm test            # vitest run
npm run check       # lint + typecheck + test (fast, no build)
npm run build       # next build (slow; CI runs this)
```

Run `npm run check` before pushing. CI runs all four (`.github/workflows/ci.yml`).

## Commit style

Conventional Commits. Type prefixes we use:

- `feat:` user-visible feature
- `fix:` bug fix
- `test:` add or strengthen tests, no source change
- `refactor:` no behaviour change
- `chore:` deps, scripts, repo hygiene
- `docs:` docs-only
- `ci:` CI / workflow / lint config
- `perf:` measurable performance change
- `security:` security-sensitive change

Scope in parentheses is optional but useful: `feat(audit): …`, `fix(billing): …`. Body explains *why*, not *what* — the diff already shows the what.

## Testing

- Vitest with `globals: true` (so `describe`/`it`/`expect` are ambient — types wired up in `tsconfig.json`).
- Test files live next to source: `src/lib/foo.ts` → `src/lib/foo.test.ts`.
- Component tests use the same runner; we don't use a separate jsdom config.
- Mock heavy collaborators (Prisma, Stripe, providers) with `vi.hoisted`; see `src/lib/audit-engine.test.ts` for the pattern.
- No DB-touching tests in unit suites. If you need integration, gate it behind an env flag and document it.

## Safety rules

These are non-negotiable:

- **No destructive DB commands** without explicit approval (`prisma migrate reset`, `db push --force-reset`, etc.).
- **No force pushes** to shared branches.
- **No real outbound** during automated work — emails, SMS, calls, public posts. If you're testing send paths, point providers at sandbox accounts.
- **No secrets in logs or commits**. The logger redacts known patterns (`src/lib/logger.ts`), but don't rely on it — pass IDs, not tokens.
- **Read-only by default**. Side effects need a clear reason, an audit log entry, and where relevant a workspace scope check.

## Pull request checklist

- [ ] `npm run check` is green locally
- [ ] New code has tests (or is purely UI / docs)
- [ ] Public-facing copy is prospect-friendly (never blames the user, never leaks internals)
- [ ] No `console.*` calls — use `logger.*` from `src/lib/logger.ts`
- [ ] No new env vars without updating `.env.example` and `src/lib/env.ts`
- [ ] Touched migrations? Doc the plan in `prisma/` before applying
- [ ] PR description explains *why* and links to any related issue/branch
